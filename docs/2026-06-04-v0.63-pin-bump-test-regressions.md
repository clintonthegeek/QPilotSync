## What this doc records

The v0.60 → v0.63 libkalburator pin bump landed with one test adaptation
(carddav e2e `dynamic_cast` updated for Plan 3 reparenting) but **three
runtime tests still fail** with the same symptom. They are deferred for a
separate triage pass rather than blocking the pin bump.

## The three failing tests

| Test | File | Failure site | Symptom |
|---|---|---|---|
| `tst_palm_runtime_route_first_sync` | `tests/runtime/tst_palm_runtime_route_first_sync.cpp:98` | `QVERIFY(fut.resultAt(0).success)` | `success == false` after `runtime.hotSync()` |
| `tst_palm_runtime_route_recategorization` | `tests/runtime/tst_palm_runtime_route_recategorization.cpp:123` | same | same |

All three fail in the SyncEngine worker's reported result, not at
compile-time, not at backend registration. Engine log shows the worker
starting (`SyncEngineWorker: === Starting sync ... ===`) then the future
resolves with `success=false`. No exception, no engine log line naming
the failure.

## What changed on v0.63 that's likely relevant

From the handoff:

- **Plan 3** — neutralize the calendar-typed sync core; non-calendar
  backends reparented onto `SyncBackendBase`; neutral `SyncOperation`
  base; engine no longer names a calendar type.
- **Plan 4** — correctness/ownership sweep; among others, "`SyncEngine`
  raw-`QFutureInterface*` leak" fix — touches how the engine returns
  its future.

The route tests register a `MockBlobBackend` through
`BlobSyncBackendWrapper::wrap(...)` with shape
`(calendar, ical)`. The carddav test uses the real
`RemoteContactsBackend` (now `SyncBackendBase`-derived). Both fail at
the same observable point.

## Confirmed root cause (2026-06-06)

Diagnosed by adding `qWarning() << fut.resultAt(0).errorMessage;` to
each failing test before its `QVERIFY` and observing the engine's
underlying error string. All three tests produce:

```
"dispatchSync: backend not found"
```

This comes from `build/_deps/libkalburator-src/src/engine/syncengine.cpp:1933-1939`:

```cpp
SyncBackend *srcBackend = m_controller->backendById(request.mapping.sourceBackend);
SyncBackend *tgtBackend = m_controller->backendById(request.mapping.targetBackend);
if (!srcBackend || !tgtBackend) {
    m_currentResult.success = false;
    m_currentResult.errorMessage = QStringLiteral("dispatchSync: backend not found");
    ...
}
```

WP implements `ISyncHost::backendById` in `PalmSyncHost` at
`src/runtime/palmruntime.cpp:92-100` as:

```cpp
return dynamic_cast<Kalburator::Sync::SyncBackend*>(
    m_registry->backendInstance(id));
```

The `dynamic_cast<SyncBackend*>` is the filter. The registry stores
`SyncBackendBase*` (Plan 3 widened it). After Plan 3, several backends
inherit ONLY `SyncBackendBase`:

- `Kalburator::Sinks::GenericSqliteBackend` — this is **`wp-hub`**, used
  as the source backend in EVERY mapping in WP (every plugin syncs
  through the hub).
- `RemoteContactsBackend` (CardDAV) — used by both carddav tests.
- The post-Plan-3 plugin backends and `FilteredCollectionBackend` route
  views may also be SyncBackendBase-only; this is the route-test path.

So `dynamic_cast<SyncBackend*>(GenericSqliteBackend*)` → nullptr,
`PalmSyncHost::backendById("wp-hub")` → nullptr, `dispatchSync` bails
with "backend not found", `success=false` propagates up to the test.

### Why all 5 mappings in the route tests fail the same way

Every route-test mapping has `wp-hub` on at least one side. Each one
fails the source/target lookup. The "Starting sync ..." log lines come
from `processSync` (line 1495), which runs BEFORE `dispatchSync` (line
1539); that's why we see all 5 banners but zero downstream activity.

### Why this is a libkalburator-side regression, not a WP-side bug

Lines 759, 764, 777, 802, 1107, 1214 of `syncengine.cpp` already use
`m_registry->backendInstance(id)` returning `SyncBackendBase*` —
i.e., the post-Plan-3 contract. But `dispatchSync` (and its peers at
lines 1709, 1868, 1931, 2592) still call `m_controller->backendById()`
expecting `SyncBackend*`. That asymmetry IS the regression: dispatchSync
should fetch backends the same way the rest of the engine does. The
inline comment in `PalmSyncHost::backendById` accurately describes the
post-P3 design ("engine fetches non-calendar backends directly from
BackendRegistry via SyncBackendBase* post-P3") — that design was
implemented in 6 sites but missed in 5 others, including dispatchSync.

The CardDAV-test compile-time `dynamic_cast<SyncBackend*>` →
`dynamic_cast<SyncBackendBase*>` fix that WAS applied in the v0.63 bump
got the WP test through the compile gate, but it didn't address the
runtime engine code path that has the same gap.

### Disposition

Handoff RFC to libkalburator written at
`docs/2026-06-06-libkalburator-dispatchsync-backendbyid-regression.md`.
Once libkalburator migrates `dispatchSync` (and the 4 sibling sites) to
`m_registry->backendInstance(id)`, all three tests should turn green
without any WP-side change.

## What WAS done in this bump

- `CMakeLists.txt:63` pin v0.60 → v0.63.
- `tests/runtime/tst_runtime_carddav_e2e.cpp`: `dynamic_cast<SyncBackend*>`
  → `dynamic_cast<SyncBackendBase*>` on both lines 111 and 173,
  matching v0.63's `RemoteContactsBackend : public SyncBackendBase`.
  Without this fix the test failed at compile-runtime boundary; with
  it, it advances to the same `success=false` failure as the other two.
- `BackendRegistry::registerBackendInstance` already accepts
  `SyncBackendBase*` on v0.63 (was `SyncBackend*` on v0.60); WP source
  was prepared for this by `a919a3c refactor(palm/todo): reparent
  PalmToDoBackend to SyncBackendBase`.
