## What this doc records

The v0.60 → v0.63 libkalburator pin bump landed with one test adaptation
(carddav e2e `dynamic_cast` updated for Plan 3 reparenting) but **three
runtime tests still fail** with the same symptom. They are deferred for a
separate triage pass rather than blocking the pin bump.

| `tst_palm_runtime_route_first_sync` | `tests/runtime/tst_palm_runtime_route_first_sync.cpp:98` | `QVERIFY(fut.resultAt(0).success)` | `success == false` after `runtime.hotSync()` |

All three fail in the SyncEngine worker's reported result, not at

the failure.

## What changed on v0.63 that's likely relevant

From the handoff:

- **Plan 3** — neutralize the calendar-typed sync core; non-calendar
  backends reparented onto `SyncBackendBase`; neutral `SyncOperation`
  base; engine no longer names a calendar type.
- **Plan 4** — correctness/ownership sweep; among others, "`SyncEngine`
  raw-`QFutureInterface*` leak" fix — touches how the engine returns
  its future.

The route tests register a `MockBlobBackend` through
`BlobSyncBackendWrapper::wrap(...)` with shape
`(calendar, ical)`. The carddav test uses the real
`RemoteContactsBackend` (now `SyncBackendBase`-derived). Both fail at
the same observable point. Hypotheses to investigate, in order:

1. **`BlobSyncBackendWrapper` does not satisfy the post-Plan-3
   `SyncBackendBase` contract** — the wrapper was written against the
   pre-Plan-3 `SyncBackend`-only world. The carddav test bypasses the
   wrapper (it uses `RemoteContactsBackend` directly) yet also fails,
   which weakens this hypothesis unless the wrapper-using setup is
   incidentally wrong in both routes too.
2. **Shape-registry / `nativeShapes()` declaration mismatch** — the
   handoff explicitly says: "Verify each conduit's
   `nativeShapes()`/`shapeFor()` is correctly declared (calendar-views-
   style; see libkalburator `INVARIANTS.md` §10)." Worth running this
   check across all 5 conduits.
3. **Plan-4 future-ownership change affects how tests observe results**
   — `fut.resultAt(0).success` may be reading a default-constructed
   `PalmRunResult` if the future result slot is populated differently
   than before. Check `runtime.hotSync()`'s return-path.
4. **Engine cancels silently** — the libkalburator INVARIANTS doc
   (Phase D harness §"Cancellation") notes Plan-4 changed cancel
   propagation. If something in the WP test setup now appears as
   "cancel" to the engine, the future resolves false. Less likely
   because the test logs show the worker reaches "Starting sync".

## Recommended triage order

1. Add a debug print at the engine result-population site in v0.63
   libkalburator and re-run `tst_palm_runtime_route_first_sync` to see
   which branch of the result-assembly fires.
2. If the symptom points at a missing/empty `pushItems` result, walk
   `BlobSyncBackendWrapper` against the new `SyncBackendBase` contract.
3. If the symptom is "no mapping executed," walk `nativeShapes()` for
   the calendar / contacts plugins.

## What WAS done in this bump

- `CMakeLists.txt:63` pin v0.60 → v0.63.
- `tests/runtime/tst_runtime_carddav_e2e.cpp`: `dynamic_cast<SyncBackend*>`
  → `dynamic_cast<SyncBackendBase*>` on both lines 111 and 173,
  matching v0.63's `RemoteContactsBackend : public SyncBackendBase`.
  Without this fix the test failed at compile-runtime boundary; with
  it, it advances to the same `success=false` failure as the other two.

  `SyncBackendBase*` on v0.63 (was `SyncBackend*` on v0.60); WP source
  was prepared for this by `a919a3c refactor(palm/todo): reparent
  PalmToDoBackend to SyncBackendBase`.
