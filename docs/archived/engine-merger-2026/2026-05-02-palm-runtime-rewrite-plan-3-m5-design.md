**Predecessors:** Plan 1 (libkalburator changes, landed),
   Plan 2 (WildPalms M2–M4, landed).
**Successor:** Plan 5 / M6 (delete `SyncRunner_wp` etc., merge to

**Status:** M5a + M5b + M5c landed 2026-05-02. M5a commits 722a6a5–b000efe
   (tag `v0.18-phase-m5a-conflict-ui`). M5b commits 81a3aa6–6339500

## 1. Why this exists

M2–M4 produced a working `PalmRuntime` and migrated five backend
plugins to `IBackendPluginV2`. The runtime is real-device
verified. What is missing is the user-facing surface area to
*drive* it without editing config files by hand:

- Conflict policy `AskUser` is wired through libkalburator's
  `ConflictHandlerRegistry`, but `PalmRuntime` does not surface
  conflict events to any GUI today, so `AskUser` is effectively
  unusable on real hardware.
- `SyncMapping` configuration is auto-generated by
  `PalmRuntime::connectDevice` (RawFiles defaults). A user who
  wants anything else has to hand-edit `.wildpalms.conf`'s
  `syncMappingsJson`.
- Five `IBackendPluginV2` plugins each implement
  `hasMainView()` / `createMainView()` (the per-plugin browse
  affordance), but we have not verified the wiring at
  `kf6mainwindow.cpp:646–653` actually populates pages for all
  five in MVP-OFF mode. Five `WILDPALMS_CALENDAR_MVP_ONLY` guards
  in `kf6mainwindow.{h,cpp}` need to come out.
- Four `_v2` integration tests (memo / contacts / todos / webcal)
  were deferred from M4 because their original form called the
  deleted F1 facade `runBlobMirror`/`runBlobTwoWay`.

M5 closes those four gaps. It does not introduce Akonadi,
GenericSqlite, or any non-RawFiles PC backend; those remain
deferred. It does not rewrite `KF6MainWindow`'s shell; per design
§7 the existing `KXmlGuiWindow` shell stays.

## 2. Scope boundary

**In scope:**
- Wire conflict events from `PalmRuntime`'s embedded
  `Kalburator::Sync::SyncEngine` to the existing
  `InteractiveConflictHandler` via the engine's
  `ConflictHandlerRegistry`.
- Net-new mapping editor (table + add/edit/delete) restricted to
  the **RawFiles** PC backend kind.
- Settings polish: backup-root configuration, plugin
  enable/disable, device-options page extension.
- Verify each `IBackendPluginV2` plugin's `hasMainView()` /
  `createMainView()` works through `KPageWidget` in MVP-OFF mode.
- Remove the five `WILDPALMS_CALENDAR_MVP_ONLY` guard sites in
  `kf6mainwindow.{h,cpp}`.
- Rewrite the four deferred `_v2` integration tests against the
  current `SyncEngine::runSyncFuture` API.
- Flip the build's default to `WILDPALMS_CALENDAR_MVP_ONLY=OFF`
  (5-plugin mode becomes default).

**Out of scope:**
- Akonadi / GenericSqlite / OrgFile PC backend integration.
- `KF6MainWindow` shell rewrite (KParts hosting, etc.).
- First-time-setup wizard (design §6 already defers it).
- Per-mapping loss-policy UI override (Profile defaults suffice
  pre-Akonadi).
- `SyncRunner_wp` / `DeviceSession` / `DeviceWorker` /
  `TickleWorker` source deletion — that is M6.

## 3. Sub-milestone slicing

M5 lands in three independently-tagged sub-milestones. Each
has its own real-device verification gate.

### M5a — Conflict UI rewiring

**Real-device gate:** HotSync with `conflictPolicy = AskUser` on
   a profile whose Palm has changes that conflict with PC-side

### M5b — Mapping editor + settings polish
**Tag:** `v0.19-phase-m5b-mapping-editor`

   chosen location.
**Estimate:** 5–7 days. The mapping editor is the largest

### M5c — Per-plugin views + `_v2` test rewrite + MVP-guard removal
**Tag:** `v0.20-phase-m5c-views-and-tests`
**Real-device gate:** build with default flags (MVP-OFF), launch
   WildPalms, verify every plugin's KPageWidget page displays

**Estimate:** 3–4 days.

**Total:** ~10–14 days. Plan 2 estimated M5 at 1.5 weeks; this
matches.

## 4. Architecture

```
┌─────────────────────── KF6MainWindow ───────────────────────┐
│ Tools menu   Settings menu   per-plugin pages (KPageWidget) │
│      │             │                  │                     │
│      ▼             ▼                  ▼                     │
│  PalmRuntime  Settings/Mapping  IBackendPluginV2            │
│   (M5a wires    editors          ::createMainView()         │
│   conflict      (M5b)            (M5c verifies)             │
│   handler in)                                               │
└─────────────────────────────────────────────────────────────┘
                       │                        │
                       ▼                        ▼
            ConflictHandlerRegistry      Profile (.wildpalms.conf
            (libkalburator)              + syncMappingsJson)
                       │
                       ▼
          InteractiveConflictHandler
            (existing, src/app/)
                       │
                       ▼ (GUI thread via blockingQueued)
                  ConflictDialog (existing, src/app/)
```

### 4.1 Architectural principles

1. **Single integration point.** Every M5 piece touches
   `KF6MainWindow` and either `Profile` (for persistence) or
   `PalmRuntime` (for runtime wiring). No new top-level
   components are introduced.
2. **Reuse-not-rebuild.** `InteractiveConflictHandler`,
   `ConflictDialog`, `SettingsDialog`, `ProfilePropertiesDialog`,
   `m_backendPluginPages` map all already exist. M5 connects
   them, does not replace them.
3. **Profile is the single config store.** Mappings, conflict
   policy, backup root, plugin enable/disable persist via the
   existing `Profile` class (`.wildpalms.conf` + JSON
   sub-payload). No new persistence layer. This resolves
   design §6's "open to KConfig-only" clause in favor of the
   status quo, since the JSON sub-payload (`syncMappingsJson`)
   is already wired.
4. **MVP-guard removal pairs with M5c.** The five
   `WILDPALMS_CALENDAR_MVP_ONLY` guards in `kf6mainwindow.{h,cpp}`
   come out together with the per-plugin-view verification —
   both gate the same "5-plugin mode is default" landmark.

## 5. Components

### 5.1 New code

- **`MappingEditorDialog`** (M5b) — `QDialog` with `QTableView`
  showing per-row plugin-id × pcBackendKind × source-collection ×
  target-collection × conflict-policy. Add/edit row opens a
  modal sub-dialog. Read/write `Profile::syncMappingsJson()`.
  ~500 lines including the row-edit sub-dialog.
- **`MappingRowDialog`** (M5b) — modal sub-dialog for adding or
  editing one mapping. Plugin-id picker (combo: enabled
  IBackendPluginV2 plugins), pcBackendKind locked to `RawFiles`,
  source-collection picker (combo populated from the selected
  plugin if the plugin's V2 contract exposes a collection-list
  affordance; otherwise free-text — exact mechanism to be
  determined during M5b implementation against the live
  `IBackendPluginV2` surface), target-collection picker
  (free-text — the
  RawFiles "collection" is just a sub-folder name), conflict
  policy combo (`Manual`/`KeepSource`/`KeepTarget`/`AskUser`).
  Path picker for the RawFiles root. ~250 lines.

### 5.2 Modified code

- **`PalmRuntime`** (M5a) — add
  `void setConflictHandler(Kalburator::Sync::QSyncCore::ConflictHandler*)`
  that forwards into `m_engine->conflictRegistry()->setDefaultHandler(...)`.
  Idempotent on re-call. Tested via direct registry inspection
  in unit tests; no GUI dependency added.
  ~30 lines including header forward declarations.
- **`KF6MainWindow`** (all sub-milestones):
  - **M5a:** construct `InteractiveConflictHandler` after
    `m_palmRuntime` is created (around line 781), pass it via
    `setConflictHandler()`. Verify the existing
    `keepAliveRequested` connection at line 811 still wires
    correctly. Verify `ConflictStore` ownership/lifetime —
    handler currently takes a non-owning pointer.
  - **M5b:** add Tools-menu (or Settings-menu) action "Configure
    mappings…" that opens `MappingEditorDialog`. Reload
    PalmRuntime's mapping list when dialog accepts (via a new
    `PalmRuntime::reloadMappings()` slot that re-reads from
    Profile and replaces `m_mappings`).
  - **M5c:** remove all 5 `#ifndef WILDPALMS_CALENDAR_MVP_ONLY`
    guard sites; flip `option(WILDPALMS_CALENDAR_MVP_ONLY ... ON)`
    to `OFF` default in top-level `CMakeLists.txt:68`.
- **`SettingsDialog`** (M5b) — extend with a new "Sync" page
  containing: backup-root path picker, plugin enable/disable
  list (synced with `Profile::conduitEnabled()`), default
  conflict policy combo. The existing Profiles/Devices/Advanced
  pages are unchanged.
- **`PalmRuntime::connectDevice`** (M5b) — defaults-creation
  logic moved behind a guard: only auto-create RawFiles defaults
  if `Profile::syncMappingsJson()` is empty. If the user has
  saved mappings, those win.

### 5.3 Code that exists but must be verified working against the post-G API

These pre-date Phase F2/G and may have drifted:

- **`InteractiveConflictHandler`** (`src/app/`) — implements
  `Kalburator::Sync::QSyncCore::ConflictHandler`. Verify the
  interface signature still matches. The handler's
  `handleConflict(ConflictRecord&, ResolutionContext&)` method
  must compile against the current `ConflictHandler` virtual
  contract. If drifted, write a thin adapter rather than
  modifying the handler in place.
- **`ConflictDialog`** (`src/app/`) — verify it instantiates
  cleanly and the existing modal-on-GUI-thread invocation still
  works.
- **`m_backendPluginPages` map population** in
  `kf6mainwindow.cpp:646–653` — verify it is reached for each
  of the five `IBackendPluginV2` plugins in MVP-OFF mode and
  that `hasMainView()` returns true for each. If a plugin
  returns false, fix the plugin (M5c task).

## 6. Data flow

### 6.1 Conflict resolution path (M5a)

```
Engine detects conflict during sync (e.g., HotSync with both sides changed)
   │
   ▼
SyncEngine::worker calls ConflictHandlerRegistry::handlerFor(backendId)
   │   (returns InteractiveConflictHandler — registered as default in M5a)
   ▼
InteractiveConflictHandler::handleConflict(record, ctx)
   │
   │   Worker thread (engine's internal thread).
   │   handleConflict marshals to GUI thread via
   │   blocking-queued connection to handleConflictOnGuiThread.
   ▼
handleConflictOnGuiThread (GUI thread)
   │
   ▼
ConflictDialog (modal)
   │
   ▼
User picks Keep-source / Keep-target / Skip / Defer
   │
   ▼
ConflictDecision returned through the marshalling chain
   │
   ▼
Engine worker resumes; applies decision; continues queue
```

The engine pauses for the duration of the dialog (synchronous
contract, by design). `keepAliveRequested` signal on
`InteractiveConflictHandler` exists for the case where the
user takes long enough that the link's keep-alive needs
poking — KF6MainWindow already connects this signal at line 811.

### 6.2 Mapping save / load (M5b)

```
KF6MainWindow ─[Configure mappings...]→ MappingEditorDialog
                                            │
                                            ▼
                       Loads Profile::syncMappingsJson()
                                            │
                                            ▼
                  WildPalmsSyncMappingHelper::parseMappings(json)
                                            │
                                            ▼
                          Render as table rows in QTableView
                                            │
                       (user edits via MappingRowDialog)
                                            │
                                            ▼
                       Serialize back via helper (toJson form)
                                            │
                                            ▼
                       Profile::setSyncMappingsJson(json) + save()
                                            │
                                            ▼
                     PalmRuntime::reloadMappings() (replaces
                     m_mappings; engine re-reads on next run)
```

### 6.3 Per-plugin view registration (M5c)

```
BackendPluginManager loads .so → emits backendPluginLoaded(plugin)
                                            │
                                            ▼
                  KF6MainWindow::onBackendPluginLoaded (line 651)
                                            │
                                            ▼
                  if (plugin->hasMainView())
                      view = plugin->createMainView(this)
                      KPageWidgetItem *item = ...
                      m_pageWidget->addPage(item)
                      m_backendPluginPages[id] = item
```

This wiring exists. M5c verifies it for each plugin and removes
the MVP guards that prevent four of the plugins from being
loaded today.

## 7. Error handling

### 7.1 Conflict handler unavailable (M5a)

If `setConflictHandler` is never called (e.g., test mode),
`ConflictHandlerRegistry` falls back to whatever default the
engine provides — currently `nullptr`, which means engine
behavior is governed entirely by per-mapping `conflictPolicy`
without escalation. `AskUser` policy without a handler should
log a warning and fall through to the policy's `fallback`
behavior (`defer` by default per `Profile::conflictFallback()`).
This is existing engine behavior; M5a does not change it, only
ensures the *production* path always has a handler installed.

### 7.2 Malformed mapping JSON (M5b)

`Profile::syncMappingsJson()` may return malformed JSON if the
file is hand-edited. The mapping editor:
- On load: invoke
  `WildPalmsSyncMappingHelper::parseMappings(json)`. If parse
  fails, show a non-modal warning ("Saved mappings could not
  be loaded; starting fresh") and seed an empty model. Do not
  auto-overwrite the malformed JSON until the user saves.
- On save: validate (every mapping has unique id, non-empty
  source/target, valid conflict policy) before writing.
  Validation failures show a modal error and prevent dialog
  acceptance.

### 7.3 Plugin view crash (M5c)

If a plugin's `createMainView` throws or returns nullptr, the
existing wiring at `kf6mainwindow.cpp:651–653` already
handles nullptr (the early-return at line 651 — `if (!plugin
|| !plugin->hasMainView()) return`). For thrown exceptions,
the plugin loader is responsible — out of M5 scope. Verification
in M5c checks the happy path; broken plugins are an M6+ concern.

### 7.4 PalmRuntime::reloadMappings during a running sync (M5b)

The mapping editor only allows "Save" if no run is in flight.
`PalmRuntime` today exposes `runStarted` / `runFinished`
signals but no `isRunning()` query; M5b adds either a
`bool isRunning() const` method or has KF6MainWindow track
running state via the existing signals and gate the
"Configure mappings…" action accordingly. Either way the
mapping editor never opens (or its Save is disabled) while a
run is in flight, preventing the engine from observing mid-sync
mapping list changes.

- **Unit:** `tst_palm_runtime_conflict_handler.cpp` — construct
  PalmRuntime, install a `MockConflictHandler` (custom
  `ConflictHandler` subclass that records invocations and
  returns canned decisions), trigger a synthetic conflict via
  `MockBlobBackend` setup, assert handler was invoked with the
  expected `ConflictRecord` and the engine applied the returned

### 8.2 M5b tests

- **Unit:** `tst_mapping_editor_dialog.cpp` — construct dialog
  with seeded Profile JSON, assert table rows match. Simulate
  add/edit/delete via dialog API (not via QTest::mouseClick —
  expose model accessors on the dialog for testability). Assert
  resulting JSON matches expected.
- **Unit:** `tst_palm_runtime_reload_mappings.cpp` — call
  `reloadMappings()` after profile change, assert
  `palmMappings()` returns the new list.
- **Unit:** `tst_palm_runtime_default_mappings_only_when_empty.cpp`
  — verify `connectDevice` does NOT auto-create defaults if
  Profile already has saved mappings.
- **Verification (manual):** real-device gate above.

  (`tst_memo_v2.cpp`, `tst_contacts_v2.cpp`, `tst_todos_v2.cpp`,

## 10. Known risks

1. **InteractiveConflictHandler API drift.** The handler was
   built against the pre-F2 `ConflictHandler` interface. If the
   virtual signature changed during F2 or G, M5a needs an
   adapter. Risk is low because Phase G touched the registry but
   not the handler-base contract; verify in M5a Task 1.
2. **`m_backendPluginPages` may be unreached for the four
   non-calendar plugins** in MVP-OFF builds because the four
   `WILDPALMS_CALENDAR_MVP_ONLY` guards in `kf6mainwindow.cpp`
   may sit on the registration path. M5c lifts the guards in
   topological order: registration first, then per-plugin code,
   then verification.
3. **`PalmRuntime::reloadMappings` re-entry.** If the user
   saves mappings while a run is in flight, the engine could
   observe a torn mapping list. The "save disabled while
   running" guard in §7.4 mitigates, but tests should also
   cover the race (synthetic delay between
   `Profile::setSyncMappingsJson` and `PalmRuntime::reloadMappings`).
4. **Build-default flip from MVP-ON to MVP-OFF in M5c.** Any
   developer who has cached a build dir from MVP-ON mode will
   see stale CMake cache misses on first reconfigure. Document
   in `OPERATIONS.md` and the M5c plan.

## 11. Implementation plan order

1. **Plan 3.5 / M5a plan doc** (next deliverable after this
   spec is approved). 8–12 tasks.
2. **Plan 3.6 / M5b plan doc** — written after M5a lands so
   that M5b can incorporate any handler-related findings from
   M5a. 15–20 tasks.
3. **Plan 3.7 / M5c plan doc** — written after M5b lands.
   8–12 tasks.

Total task count across the three plans is expected to land
in the 30–40 range. This is heavier than Plan 2's 20 tasks for
M2–M4 because M5 contains the largest single net-new GUI
surface (the mapping editor) and verifies a chunk of legacy GUI
code that has not been exercised since Phase F2. The
sub-milestone slicing keeps each individual plan's scope
tractable.

## 12. Open questions / deferred decisions

- **Per-plugin "Configure plugin..." button in mapping editor.**
  IBackendPluginV2 plugins may want to expose plugin-specific
  config (e.g., webcal feed URL). The current plan punts: each
  plugin is responsible for its own config UI, surfaced from
  the per-plugin view (M5c). A "Configure plugin..." button in
  the mapping editor is deferred. Revisit if a plugin actually
  needs it.
- **Mapping editor's "test mapping" affordance.** A "Try this
  mapping" button that runs a single mapping in dry-run mode
  would be useful but requires an engine flag that does not
  exist today. Deferred; would be its own libkalburator change.
- **Conflict-store badge on plugin pages.** The
  `ConflictStore` exists and tracks pending conflicts. A badge
  on the per-plugin page indicating "3 conflicts pending"
  would be nice; deferred to post-M5 polish.
